## 0. 文档目的与范围

### 0.1 目的

本文档定义"低空具身智能体"项目中**第一/三人称操纵数据采集与管理软件**的完整架构设计、模块划分、接口规范、数据流设计与部署方案，作为 T0+5 月交付物，指导软件开发、数据采集执行与数据资产管理。

### 0.2 范围

- **采集端**：第一人称座舱视角（HUD/仪表/操纵杆）+ 第三人称机外跟随视角（机动动作/机体姿态/环境）的同步视频采集
- **数据端**：56Hz 飞控操纵量（总距/周期变距/脚蹬）与视频帧的毫秒级时间戳对齐
- **管理端**：≥1000 小时操纵数据的存储、索引、检索、标注、版本管理与质量监控
- **不包含**：飞行控制算法开发、仿真环境搭建、机械臂操控软件（属轨道 A/D 范围）

| 有效数据 | 满足质量标准（无丢帧、时间对齐误差<10ms、操纵量完整、元数据齐全）的采集数据 |

## 1. 系统总体架构

### 1.1 设计原则

1. **双视角同源同步**：第一/第三人称视频由同一触发信号启动，硬件级同步，帧间误差 < 1ms
2. **毫秒级时间对齐**：所有数据流（视频帧、操纵量、状态量）统一挂载到 PTP 精确时钟基准
3. **采集即标注**：采集过程中自动写入元数据（时间戳、飞行阶段、操纵量快照），减少后处理
4. **分层存储**：热数据（最近 30 天）SSD 高速存储，温数据（30天-1年）NAS 存储，冷数据（>1年）对象存储归档
5. **可复现可审计**：每条数据带唯一 ID、采集配置哈希、质量报告，支持全链路追溯

### 2.3 飞控操纵量采集单元

#### 2.3.1 采集信号

| 信号 | 频率 | 位宽 | 接口 | 说明 |
|------|:---:|:---:|------|------|
| 总距 (Collective) | 56 Hz | 16bit | CAN Bus | 0-100%，主旋翼拉力 |
| 周期变距-纵向 (Cyclic-Lon) | 56 Hz | 16bit | CAN Bus | -100%~+100%，前后倾斜 |
| 周期变距-横向 (Cyclic-Lat) | 56 Hz | 16bit | CAN Bus | -100%~+100%，左右倾斜 |
| 脚蹬-左 (Pedal-L) | 56 Hz | 16bit | CAN Bus | -100%~+100%，偏航控制 |
| 脚蹬-右 (Pedal-R) | 56 Hz | 16bit | CAN Bus | -100%~+100%，偏航控制 |
| 飞行状态字 | 56 Hz | 32bit | CAN Bus | 飞行阶段/模式/告警 |
| 位置 (Lat/Lon/Alt) | 10 Hz | 64bit | UDP/GNSS | GPS/INS 融合位置 |
| 姿态 (Roll/Pitch/Yaw) | 56 Hz | 32bit | CAN Bus | 欧拉角 |
| 速度 (Vx/Vy/Vz) | 56 Hz | 32bit | CAN Bus | 地速分量 |

#### 2.3.2 数据格式

操纵量以 **CSV + Parquet** 双格式存储：
- **CSV**：人可读，便于快速检查
- **Parquet**：列式存储，高效压缩，便于大规模分析

每条记录格式：
```
timestamp_unix_ns, collective, cyclic_lon, cyclic_lat, pedal_l, pedal_r, 
flight_phase, lat, lon, alt, roll, pitch, yaw, vx, vy, vz, status_word
```

`timestamp_unix_ns` 为 PTP 同步的纳秒级 Unix 时间戳，与视频帧时间戳共用同一时钟基准。

### 2.4 硬件同步与时间戳模块

#### 2.4.1 时钟同步方案

采用 **PTP (IEEE 1588-2008) 精确时间协议**：

```
┌──────────────────┐
│  PTP Grandmaster  │  ← GNSS  disciplined oscillator (OCXO, <1ppb)
│  (核心服务器)      │
└────────┬─────────┘
         │ PTP over Ethernet (10GbE)
    ┌────┴────┬────────┬────────┐
    ▼         ▼        ▼        ▼
 FPV采集盒  TPV采集盒  飞控采集  处理服务器
 (PTP Client)(PTP Client)(PTP Client)(PTP Client)
```

- 同步精度：**< 100ns**（局域网内 PTP 硬件时间戳）
- 所有设备的系统时钟通过 PTP  disciplined
- 视频帧时间戳在采集盒硬件层面注入（曝光时刻的 PTP 时间戳）
- 操纵量采样点时间戳在 CAN 控制器硬件层面注入

#### 2.4.2 采集启动同步

所有采集单元通过**硬件触发信号**同步启动：
- 核心服务器发出 GPIO 触发脉冲（上升沿）
- 所有采集盒的触发输入端口同时收到脉冲
- 脉冲上升沿的 PTP 时间戳作为本次采集的 `session_start_time`
- 触发误差：**< 1μs**

#### 2.4.3 帧级时间戳注入

每帧视频在编码前写入**SEI 补充增强信息**：
```
SEI Payload:
  - frame_index: uint32 (帧序号, 从0开始)
  - timestamp_pts_ns: uint64 (PTP 纳秒时间戳, 曝光中点)
  - camera_id: uint8 (相机标识)
  - exposure_time_us: uint32 (曝光时长, 微秒)
  - gain_db: float32 (增益)
  - checksum: uint32 (CRC32 校验)
```

操纵量每条记录自带 `timestamp_unix_ns`，与视频帧共用 PTP 时钟。

## 3. 数据处理管线设计

### 3.1 管线总览

```
采集完成 → 上传 → 完整性校验 → 时间对齐验证 → 片段切分(Episode)
    → 元数据注入 → 质量检测 → 缩略图/预览生成 → 索引构建 → 入库归档
```

### 3.2 时间对齐验证

#### 3.2.1 对齐算法

对每个 Episode，验证视频帧与操纵量的时间对齐：

1. 从视频 SEI 提取每帧 `timestamp_pts_ns`
2. 从操纵量 CSV 提取每条 `timestamp_unix_ns`
3. 对每帧，找到时间戳最接近的操纵量采样点
4. 计算时间差 `Δt = |frame_ts - control_ts|`
5. 统计 Δt 的分布（均值、P50、P95、P99、max）

#### 3.2.2 对齐质量标准

| 指标 | 合格阈值 | 说明 |
|------|:---:|------|
| Δt 均值 | < 5ms | 平均对齐误差 |
| Δt P99 | < 10ms | 99% 帧的对齐误差 |
| Δt max | < 20ms | 最大对齐误差 |
| 操纵量覆盖率 | > 99.9% | 视频帧时间范围内操纵量无缺失 |
| 帧率稳定性 | > 99.5% | 实际帧率与标称帧率偏差 < 0.5% |

不满足标准的 Episode 标记为 `alignment_failed`，进入人工复核队列。

### 3.3 Episode 片段切分

#### 3.3.1 切分规则

一次完整采集（从触发启动到停止）可能包含多次起飞-着陆循环。按以下规则切分为独立 Episode：

1. **飞行阶段检测**：基于飞控状态字的 `flight_phase` 字段
   - `GROUND` → `TAKEOFF` 过渡点 = Episode 起点
   - `LANDING` → `GROUND` 过渡点 = Episode 终点
2. **悬停检测**：连续 > 30s 处于地面且操纵量接近中立位 = 两次飞行的间隔
3. **手动标注**：操作员可在采集日志中标记 Episode 边界，覆盖自动切分

### 3.4 质量检测规则引擎

#### 3.4.1 检测项

| 类别 | 检测项 | 合格标准 | 不合格处理 |
|------|--------|:---:|------|
| 视频 | 丢帧率 | < 0.1% | 标记 `frame_loss` |
| 视频 | 花屏/黑帧 | 0 帧 | 标记 `corrupted_frame` |
| 视频 | 曝光异常 | < 1% 帧 | 标记 `exposure_issue` |
| 视频 | 焦距/对焦 | 全程清晰 | 标记 `focus_issue` |
| 音频 | 音频缺失 | 无 | 标记 `no_audio` |
| 操纵量 | 采样丢包 | < 0.01% | 标记 `control_loss` |
| 操纵量 | 值域越界 | 0 | 标记 `control_out_of_range` |
| 操纵量 | 中立位漂移 | < 2% | 标记 `control_drift` |
| 时间 | 对齐误差 | P99 < 10ms | 标记 `alignment_failed` |
| 时间 | 时钟跳变 | 0 | 标记 `clock_jump` |
| 元数据 | 字段完整性 | 100% | 标记 `metadata_incomplete` |
| 元数据 | ID 唯一性 | 100% | 标记 `duplicate_id` |

#### 3.4.2 质量评分

综合质量评分（0-1）：
```
quality_score = 1.0 - Σ(weight_i × violation_rate_i)
```

| 检测项 | 权重 |
|--------|:---:|
| 丢帧 | 0.20 |
| 操纵量丢包 | 0.20 |
| 对齐误差 | 0.25 |
| 花屏/黑帧 | 0.15 |
| 元数据缺失 | 0.10 |
| 其他 | 0.10 |

- `quality_score ≥ 0.95` → 优质数据（可用于训练/评测）
- `0.80 ≤ quality_score < 0.95` → 合格数据（可用于分析，需标注）
- `quality_score < 0.80` → 不合格数据（隔离，人工复核后决定保留或删除）

### 4.2 存储方案

#### 4.2.1 分层存储策略

| 层级 | 介质 | 保留期 | 访问频率 | 用途 |
|------|------|:---:|:---:|------|
| 热数据 (Hot) | NVMe SSD | 30 天 | 高 | 最近采集、正在标注、训练中使用 |
| 温数据 (Warm) | NAS (HDD RAID6) | 30天-1年 | 中 | 历史数据检索、分析、评测 |
| 冷数据 (Cold) | 对象存储 (S3兼容) | >1年 | 低 | 长期归档、合规留存 |

数据自动迁移：
- 采集完成 → 热数据
- 30 天后无访问 → 自动迁移到温数据
- 1 年后无访问 → 自动迁移到冷数据（归档前生成完整性校验报告）
- 访问冷数据时自动回取到温数据（按需）

#### 4.2.3 存储容量估算

| 数据流 | 码率/大小 | 每小时 | 1000小时 |
|--------|:---:|:---:|:---:|
| FPV 主相机 (4K60 H.265) | 50 Mbps | 22.5 GB | 22.5 TB |
| FPV 仪表相机 (1080p60) | 15 Mbps | 6.75 GB | 6.75 TB |
| FPV 操纵杆相机 (1080p60) | 15 Mbps | 6.75 GB | 6.75 TB |
| TPV 跟随相机 (4K60) | 50 Mbps | 22.5 GB | 22.5 TB |
| TPV 固定机位 ×2 (4K30) | 20×2=40 Mbps | 18 GB | 18 TB |
| 操纵量 (Parquet) | ~50 KB/s | 180 MB | 180 GB |
| 元数据/索引/缩略图 | — | ~500 MB | 500 GB |
| **合计** | **185 Mbps** | **~77 GB/h** | **~77 TB** |

考虑 RAID 冗余（RAID6 约 1.4×）、备份（2×）、预留空间（1.3×）：
- **原始数据**：~77 TB
- **含冗余+备份+预留**：~77 × 1.4 × 2 × 1.3 ≈ **280 TB**

建议配置：核心存储 300 TB 可用容量（NAS 扩展柜 + 对象存储）。

### 4.3 索引与检索

#### 4.3.1 Elasticsearch 索引

为 Episode 级元数据建立 Elasticsearch 索引，支持全文检索和多维筛选：

**索引名**：`episodes-v1`

**可检索字段**：
- 全文：`pilot_id`, `location`, `maneuver_tags`, `flight_phases`, `annotations.label`
- 范围：`duration_s`, `start_time`, `quality_score`, `n_frames_total`
- 精确：`episode_id`, `session_id`, `aircraft_id`, `storage_tier`, `quality_flags`
- 地理：`location` (geo_point)

#### 4.3.2 检索 API

```
GET /api/v1/episodes?
  maneuver_tags=起飞,悬停,前飞
  quality_score_min=0.95
  duration_min=60
  duration_max=300
  location=南昌
```

对于需要精确到帧的检索（如"找到所有左转角度>30°的帧"），通过操纵量 Parquet 文件的列式查询实现：
- 使用 DuckDB / Polars 对 Parquet 进行列式过滤

- 查询结果返回帧时间戳列表，可跳转至对应视频帧

## 9. 数据安全与合规

### 9.1 访问控制

- 基于角色的访问控制 (RBAC)：管理员/数据工程师/标注员/审计员/只读用户
- 所有 API 接口需 JWT 认证
- 敏感操作（删除/导出/修改元数据）需二次确认 + 审计日志
- 数据文件访问通过预签名 URL（有效期 1 小时）

### 9.2 数据完整性

- 每个文件写入后计算 SHA-256 校验和，存入元数据
- 定期（每月）全量校验，检测静默数据损坏
- 冷数据归档前生成完整性报告，归档后每年抽检
- 重要数据（优质训练数据）异地备份

### 9.3 审计日志

所有操作记录审计日志（不可篡改）：
- 用户登录/登出
- 数据查询/下载/导出
- 元数据修改/标注创建/删除
- 系统配置变更
- 告警事件

审计日志保留 ≥ 3 年。
