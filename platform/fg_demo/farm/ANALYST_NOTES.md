## [2026-08-29 05:15] 批次 3：timeout 的真相 = 翻覆恢复死锁；not-ready 第二形态 = 没等 FDM 初始化

### 发现 5：绝大多数"失败回合"将表现为 timeout+max_phase=2，且每个浪费整整 240 秒

**XML 死锁机制**（`demo_stabilizer.xml` rollover guard，已逐行核对）：

```nasal
if (recovering == 1) {
    ...
    if (abs(roll) < 3.0 and agl < agl0 + 0.4) {  # 扶正成功才清 recovering
        recovering = 0; ...
    } elsif (attempts > 4) {                       # abort 挂在扶正分支下！
        ...abort...
    }
}
```

- 第一次翻覆后 `attempts=1, recovering=1`；若飞机侧躺扶不正（roll 恒 >3°），`elsif (attempts>4)` 因 attempts=1 永不触发，也永远进不了扶正分支 → **recovering=1 死锁，seq 卡在 phase 2，run=1**，直到外环 240s 超时。
- 直接证据：05:10 探针读 B 实例 `roll=+160.9°, phase=2, seq_run=1, crashed=false`——侧躺 10 分钟级别，仍在"恢复"。
- ep1 的首条有效样本（iter2, ffw=1.77, timeout, max_phase=2, t=240.4s）即此模式。

**对操作员的两个建议（合计可把失败回合成本从 240s 降到 ~10s，吞吐提升 6-12 倍）**：
1. `farm_worker.run_episode()` 增加中止判据：`/demo/seq/run` 从 1 变 0（XML abort 路径）或 `phase==0 且 seq_run==0 且已 start` → 立即 return timeout。XML 的 abort 会置 run=0，worker 现在看不见它。
2. XML 侧修复死锁：把 `attempts>4` 判断移出扶正分支（如 `recovering==1 且 roll 恒>15 持续 N 秒 → abort`），或在 recovering 分支加 `t_recover > 8s → abort`。

**注意**：修复死锁不等于修复翻转——扶正失败的根因还是 liftoff 翻覆本身；但修好后 farm 每 4 分钟能多测 2-6 个参数点，4 小时预算下是天壤之别。
