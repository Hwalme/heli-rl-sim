# 低空具身智能 · 坠机根因诊断 与 训练方法研究报告

> **写给执行训练的 Agent**：这份报告由另一个研究会话产出。先读 §1 搞清楚"为什么起飞即坠机、为什么原地空转"，再按 §6 的行动清单逐步执行。本报告附带了**已经跑通并验证的 RL 训练参考实现**（`rl_train/` 目录），不要再用 FlightGear 实时回路做训练。

---

## 0. TL;DR

1. **"瞬间坠机"的根因不是参数没调好，而是控制通道接错了 + 起飞阶段故意关闭了姿态增稳**（证据见 §1，来自你们自己的 `flight_log.json` 和代码行号）。
2. **"原地呆很久"的根因**：(a) 开环保持总距只会停在力的平衡点，没有任何反馈回路会去"调整好起飞"；(b) 每轮飞行的发动机启动/复活流程要阻塞 1~3 分钟真实时间。
3. **FlightGear 实时渲染回路从架构上就不可能完成训练**：RL 需要十万到十亿步交互，实时仿真器一辈子都跑不完。训练必须换到**无头、快速、可并行**的环境里，FlightGear 只留作最终可视化。
4. 本仓库新增 `rl_train/`：一个修好了物理 bug 的 Gymnasium 直升机环境 + PPO 训练脚本，**已在本地实跑验证**：启发式基准 20/20 起飞成功零坠毁；PPO 训练 199 秒（100 万步）后确定性策略 **20/20 全成功**。§5 还完整记录了一次"策略拒绝起飞"的失败及其修复（势函数奖励塑形）——**这是理解"为什么连起飞都学不会"的最短路径，务必先读**。

## 1. 现有代码逐条诊断（对照文件与行号）

### 1.1 `helo_fg_loop.py` —— 写错了控制通道：throttle ≠ collective（起飞指令无效）

第 202-204 行，起飞阶段写的是**发动机油门**：

```python
def phase_set(coll):
    fg.set('/controls/engines/engine[0]/throttle', coll)
    fg.set('/controls/engines/engine[1]/throttle', coll)
```

FlightGear 的 Bo-105（YASim）中，`throttle` 是发动机功率，由恒速调速器自动维持旋翼转速（442 RPM），**它不改变旋翼总距桨角**。真正控制升力的是总距杆：

```
/controls/engines/engine[0]/collective   （部分版本为 /controls/collective）
```

**铁证**（你们自己的 `flight_log.json`）：脚本记录 `coll=0.72` 保持不变，直升机被钉在 `agl=3.9 ft`、`vertical-speed ≈ 0.003 fps` —— 即升力恰好在某个平衡点，**不爬升也不坠落，原地悬停**。这正是"每次都原地呆很久"的直接原因之一：你保持的是油门，不是总距，总距根本没动。

**修复**：通过 telnet 用 `ls /controls` / `dump /controls` 确认本机 Bo-105 的总距属性路径（也可查 FGData 里 `Aircraft-bo105-set.xml` 的 `<control-input>` 绑定），然后把 `phase_set` 改写 collective 属性，双发都写。

> **【2026-08-28 勘误更新 · 来自 B 轨道实测】**：B1 修复者在 FG 2024.1 本机实测发现：**本机 bo105 的总距实际绑定在 `throttle` 属性上，且方向反向（值越小升力越大）**。即本节"改写 collective"在本机不成立，以 `platform/` 轨道 B1 文档实测确认的属性与方向为准。教训：FG 属性绑定随版本与机型配置而异，**任何属性写入前必须在该机实测校验方向与响应**。

### 1.2 `helo_fg_loop.py` 第 231-235 行 —— 起飞阶段强制关闭姿态增稳 → 离地即翻滚

```python
# 地面/离地瞬间: 零操纵, 让直升机直升机干净离地
fg.set('/controls/flight/aileron', 0)
fg.set('/controls/flight/elevator', 0)
fg.set('/controls/flight/rudder', 0)
```

Bo-105 在悬停附近**静不稳定**（无 SAS/增稳时是公认最难飞的直升机之一）。起落橇卸载的瞬间，任何微小扰动（风、配平误差）都会发散。你们把增稳内环在起飞阶段关掉，直升机一离地就滚转发散，`is_crashed` 检测到 `roll>90°` 或 `pitch>60°` 判坠 —— 这就是"**瞬间坠机**"。

**修复**：离地检测（`agl > 0.5 ft`）后**立即**切入姿态 PD 内环（第 242-245 行已有切入逻辑，但阈值 5 ft 太晚、增益 0.035 太弱）。增稳要贯穿整个起飞过程，且 PD 增益和控制周期（0.25 s 太慢，建议 ≤0.1 s）都要加大加密。

### 1.3 `启动FlightGear.bat` / `helo_sim.py` —— 通信架构三方矛盾，控制可能根本没接到飞机上

三个脚本对 FlightGear 的假设互相冲突：

| 组件 | 假设 | 问题 |
|------|------|------|
| `启动FlightGear.bat` | `--fdm=external` + generic UDP 5500/5501 | `--fdm=external` 会**绕过 Bo-105 自带物理**，此时通过属性树写 `/controls/*` 对飞行动作**完全无效**；且 generic 协议需要一个 XML 协议文件名，直接发 `属性名 值\n` 文本行（`helo_sim.py` 的做法）不是合法格式，会被丢弃 |
| `helo_sim.py` / `helo_sim_auto.py` | UDP 文本协议控制 | 同上，包会被静默忽略 |
| `helo_fg_loop.py` | TCP telnet 连 5501 | bat 里 5501 是 **UDP generic 出口**，不是 telnet 服务器；除非 FG 用 `--telnet=...` 启动，否则这个 TCP 连接会超时失败 |

**修复（若仍要用 FlightGear 做可视化）**：统一为一种配置——

```
fgfs --aircraft=bo105 --telnet=socket,in,5,127.0.0.1,5501,tcp,prompt
```

去掉 `--fdm=external`（用原生 YASim 物理），去掉 `--generic`。控制走 telnet 属性树，状态也走属性树（`/position/altitude-ft`、`/orientation/*`、`/velocities/*`、`/rotors/main/rpm`）。

### 1.4 启动/复活流程分钟级阻塞 —— "原地呆很久"的另一半原因

`start_engines()`（第 138-191 行）：启动机等待循环最长 90 s（3 s 一轮轮询）+ 旋翼建速等待 60 s + 坠机后 reinit 1.5+6 s + telnet 每条指令一次阻塞往返。**每一轮飞行的固定开销是 1~3 分钟墙钟时间**，坠机后还要重来。执行 agent 的大部分"工作"时间其实烧在等旋翼转起来。

### 1.5 简化动力学脚本（`helo_sim_final.py` / `helo_sim_auto.py`）的两个物理 bug

1. **地面效应硬切换**（第 74-79 行）：高度=0 时升力 ×1.2，一离地立刻 −20%。总距落在 0.555~0.666 区间时，直升机会"跳起→摔回→再跳起"无限循环，看起来就是贴地弹跳/呆滞。`rl_train/helo_env.py` 已改为随离地高度指数平滑衰减。
2. **纯开环、无反馈**：`helo_sim_final.py` 是按脚本时间表推关节的演示，不是闭环控制，更不是训练。开环保持总距只能停在平衡点——**"调整好起飞"这件事本质上需要一个反馈控制器**，这正是要用 RL/控制理论解决的问题，靠时间表演不出来。

### 1.6 定量账：为什么 FlightGear 实时回路不可能完成训练

| 方案 | 每秒环境步数 | 训练 10⁷ 步需要 |
|------|-------------|----------------|
| FlightGear 实时 + telnet（现状） | ~4 步/秒（0.25s 周期），且 1×墙钟 | **约 29 天（还不含每轮 1~3 分钟启动）** |
| `rl_train/helo_env.py` + 8 并行（本仓库） | 实测见 §5 | **约 1~3 分钟** |
| Isaac Lab / OmniDrones 单张 RTX | 10⁶~10⁷ 步/秒 | 分钟级 |

结论：**不是你们不够努力，是工具选错了。**

## 2. 方法综述：业界如何训练低空具身智能（六大家族）

| # | 方法 | 核心思想 | 样本效率提升 | 代表工作/仓库 |
|---|------|---------|------------|--------------|
| A | **GPU 大规模并行 RL** | 单卡同时推进 4096~16384 个环境，状态留在显存，**训练全程不渲染画面** | 10⁴~10⁶×；悬停/跟踪策略 10~30 分钟收敛 | [btx0424/OmniDrones](https://github.com/btx0424/OmniDrones)（Isaac Sim 无人机 RL 平台）、Aerial Gym（NTNU）、Isaac Lab、[Genesis-Embodied-AI/Genesis](https://github.com/Genesis-Embodied-AI/Genesis)（免费开源） |
| B | **教师-学生特权蒸馏** | 先用全状态观测（真值位置/风速）训 teacher，再蒸馏给只有机载传感器（深度图/IMU）的 student | 训练期完全不渲染视觉，省掉最大开销 | ETH 无人机竞速冠军系统 Swift（Nature 2023）同款范式 |
| C | **模仿学习 → RL 微调** | 少量示范做行为克隆/DAgger 起步，再 PPO 微调 | 对"机械臂操纵杆"这类高维连续动作空间，比纯 RL 从零探索省 10~100× | LeRobot、Diffusion Policy、ACT |
| D | **层次化分解** | 底层悬停/姿态给经典控制器（PID/几何控制/PX4），只学上层任务决策 | 学习难度骤降，训练量骤降 | 几乎所有实机部署的标准架构 |
| E | **VLA 基础模型微调** | 不从零训练，拿预训练视觉-语言-动作模型做 LoRA 微调 | 起点自带"世界知识" | [openvla/openvla-7b](https://huggingface.co/openvla/openvla-7b)（64k 下载） |
| F | **世界模型 / Model-based RL** | 先学环境动力学模型，在"想象"中规划 | 比 model-free 省 10~50× 样本 | DreamerV3 |

**对本项目的映射**：你们的"机械臂飞行员"概念，标准做法是 **C（先示范后强化）+ D（机械臂关节层不做端到端）**：把机械臂→操纵机构的映射当作动作空间的一层（`helo_env.py` 的 `arm` 模式已实现），底层飞行稳定性让 RL 或经典控制去解决。

## 5. 本仓库新增参考实现（已验证）

```
rl_train/
├── helo_env.py          # FastHeloEnv: 修好地面效应/推力标定的 Gymnasium 环境
│                        #   action_mode="direct"（总距/俯仰/滚转/尾桨）或 "arm"（7 关节，helo_sim_final 同款映射）
│                        #   域随机化：每回合随机目标高度 25-70m、风、质量扰动；坠毁判定与 helo_fg_loop 语义一致
├── heuristic_check.py   # 手写 PD 基准：验证环境可解 + arm 模式冒烟测试
└── train_ppo.py         # SB3 PPO 训练入口，输出 results/helo_ppo.zip + results.json
```

**已验证结果**（本机实跑）：

- 环境自检：满总距 300 步爬升到 75.4 m，无坠毁；悬停总距标定 0.7007。
- 启发式 PD 基准：**20/20 回合成功起飞并悬停到目标高度，0 坠毁**，最终高度误差 ~1.3 m。
- arm 模式：关节 0=1.0 时 100 步内离地 6.9 m，映射链路通。
- PPO 训练（**含一次失败，这一课最重要**）：
  - **v1（失败）**：奖励只有 `-|alt_err|` 项时，训满 400k 步，策略学会"**永远趴在地上**"——成功率 0%、坠毁率 0%、平均高度误差恒定 ~52m。原因：**地面是死锁平台**——在地面时任何动作都不改变状态（无因果信号），而早期随机飞行只会挨罚（姿态惩罚+坠毁扣分）→ 策略收敛到"不起飞"局部最优。**注意：这与执行 agent "连起飞都做不到"的现象同构**——不是探索不够、不是参数没调好，是奖励结构没有给"起飞"这个动作提供任何梯度。
  - **v2（成功）**：改用**势函数奖励塑形**（potential-based shaping）`r += (prev_alt_err − alt_err)`，即"每向目标靠近 1 米立即 +1.0"，起飞动作从一开始就有正梯度；再加起飞拖延惩罚（离地 2.5s 后仍趴地 -0.05/步）、悬停保持奖励（误差<5m 且姿态平稳 +0.5/步）、熵系数提到 0.01 帮助探索。
  - **v2 最终结果**（本机实跑）：1,000,000 步，8 并行环境，纯 CPU；训练耗时 **199 秒**（5,024 steps/s）。成功率曲线：0%(600k 前) → 83%(700k) → **100%(800k 起)**；最终确定性策略评估 **20/20 回合成功起飞并悬停到随机目标高度（25-70m），坠毁率 0%，平均高度误差 6.80 m**。
  - 产物：`rl_train/results/helo_ppo.zip`（策略）、`rl_train/results/helo_ppo_results.json`（指标）。
  - 对照账：同一台机器，FlightGear 实时回路跑 100 万步需要 **约 8 个月**；这里用了 **3.3 分钟**，加速比约 10⁵。

**复现命令**：

```bash
cd rl_train
python heuristic_check.py          # 先跑这个，确认环境通
python train_ppo.py --steps 400000 # PPO 训练（几分钟）
python train_ppo.py --arm          # 可选：机械臂关节动作模式
```

**已知边界（诚实声明）**：`helo_env.py` 是质点+一阶姿态的简化动力学，用于**验证方法与训练管线**；策略迁移到 Bo-105/YASim 或真实机体时需要系统辨识 + 域随机化微调。这正是业界标准流程（§2-B），不是缺陷。

## 6. 给执行 Agent 的行动清单

1. **读本报告 §1**，逐条对照你现有代码，确认你踩了哪几条（大概率 1.1 + 1.2 同时存在）。
2. **立即停止**在 FlightGear 实时回路上做"训练"——它只能当演示。
3. 运行 `cd rl_train && python heuristic_check.py`，确认输出 `[PASS]`。
4. 运行 `python train_ppo.py --steps 400000`，观察成功率爬升；完成后读 `results/helo_ppo_results.json`。
5. （可选，做演示用）按 §1.3 修复 FlightGear 启动参数与总距属性，把训练好的策略接到 FG 上可视化。
6. 下一阶段按 §4 路径 2 升级到 gym-pybullet-drones / Isaac Lab / Genesis。
